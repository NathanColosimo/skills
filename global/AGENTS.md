- Before filing, updating, or reviewing a PR, apply the `standards` skill. When writing a PR description or posting a PR comment, follow the `pr-writing` skill.

## How to respond

When you report on work in a thread, use these sections, in this order. Leave out any section that would be empty. Keep every key detail, but say each thing once.

1. **Summary**: what I need to know, the important details, and why they matter. A few lines.
2. **Status**: what you actually did, and how far it got. Be exact about what is and isn't done or tested. For example: "PR open, CI running"; "PR open, CI failed on lint"; "changes on a local branch, no PR yet, unit tests pass"; "training run started, not finished"; "code written, not tested"; "planned only, no code yet"; "ideas only, none tried".
3. **The main content**, under a heading that names it: the answer, the findings, the plan, or the changes.
4. **Also noticed**: things outside what I asked for that I'd want to know, kept out of the main content so they aren't buried. A bug you found (and whether you fixed it, confirmed it, or only have ideas), a simplification you made or suggest, work someone else already did, a risk.
5. **Needs you**: decisions, actions, or blockers waiting on me, and the next steps, with your recommendation first.

Use short sentences, lists, and tables where they help. Don't pad, and don't narrate your process. Leave out details that don't change what I know or do, like a tool hiccup or a mistake you already fixed along the way.
